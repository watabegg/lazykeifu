# lazykeifu 開発計画書

> M0は完了しています。M1の初回実装と現時点の制約は[workspace-m1.md](workspace-m1.md)を参照してください。以下は初期化時に定めた計画です。

## 目的と基本合意

日常の開発において、端末マルチプレクサの Herdr を利用し、画面左側に lazygit、右側に keifu を並行起動して運用している。しかし現状の構成では、対象コミットやファイルの選択、ペイン間のフォーカス移動、外部変更時の表示更新をそれぞれのツールで個別に行う必要があり、二重の操作負担が生じている。

この課題を解決するため、keifu の視認性に優れたコミットグラフ描画と、lazygit の洗練された画面構成および操作感を統合した軽量 TUI ツールを開発する。プロジェクトの仮称は lazykeifu とし、実装言語には Rust を採用する。

本計画では、lazygit の全機能を網羅的に移植することや、Go 言語で書かれたコードを逐語訳することは対象外とする。keifu をフォークして機能拡張の母体とし、lazygit のフォークリポジトリは操作体系や振る舞いの参照用として活用する。

## 確認済みの現状と課題

### 既存コードベースとリポジトリ構成
keifu はバージョン 0.7.0（コミット `015f0b25b85d068b1e2c8c0c8c137bc87d4b7c91`）を基点とする。Rust のエディションは 2021 であり、主要クレートとして ratatui 0.29、crossterm 0.28、git2 0.19 を利用している。

GitHub 上には以下のフォークを作成済みである。
- lazykeifu: [https://github.com/watabegg/lazykeifu](https://github.com/watabegg/lazykeifu)（親リポジトリ: trasta298/keifu）
- lazygit: [https://github.com/watabegg/lazygit](https://github.com/watabegg/lazygit)（親リポジトリ: jesseduffield/lazygit）

ローカル環境の origin は lazykeifu、upstream は keifu を指すように構成し、keifu のコミット履歴をそのまま維持する。ライセンスはいずれも MIT License である。keifu の LICENSE ファイルを維持し、将来 lazygit のコード等を取り込む場合はその著作権表示も保持するが、現時点で lazygit のソースコードを製品コードへ直接コピーすることはない。なお、ベースラインおよび初期化の動作検証は完了しており、テスト（計 113 件成功）や静的解析・フォーマットの通過、一時リポジトリのデバッグサーバを用いた画面描画や操作、設定分離の確認結果を `docs/bootstrap-validation.md` に記録している。

### lazygit の参照状況
lazygit はコミット `4e1eebe278790f257a875da6633234391a5a85b3` を参照している。`pkg/config/user_config.go` の定義から、`j` / `k` によるカーソル移動、`h` / `l` によるブロック間移動、`Tab` / `Shift-Tab` によるペイン巡回、`1` 〜 `5` のペイン指定、`0` によるメインビュー移動、`Space` による選択、`Enter` による詳細遷移、`c`（コミット作成）、`P`（プッシュ）、`p`（プル）、`s`（スタッシュ）などの基本キーバインドを確認している。ただし、全体や個別コントローラの文脈まで完全に検証したわけではない。

### keifu の内部構造と技術的課題
- **状態管理と非同期処理（`src/app.rs`）**: `AppMode` と `FocusedPane`（Graph / Detail）に操作状態が集約されている。差分計算はスレッドと mpsc チャネルによる非同期処理である一方、`main.rs` のローカル更新は同期実行され、待機（idle）後に処理される。コミット履歴の取得件数は上限 500 件に制限されている。
- **画面表示とキー操作（`src/ui/mod.rs`、`src/mouse.rs`、`src/keybindings.rs`）**: `ui/mod.rs` のレイアウトと `LayoutMap`、`mouse.rs` の矩形ヒット判定、`keybindings.rs` のモード別 `Action` 変換で構成されている。単にキー割り当てを差し替えるだけでは独立した複数ペインの操作は成立しない。
- **差分表示の制約（`src/git/diff.rs`）**: 変更ファイルの表示上限が 50 件に固定されており、ステージ済み、未ステージ、未追跡のファイルが混在して一覧表示される。日常的な利用に耐えるクライアントとするには、全変更へ到達できる仕組みが必要である。
- **Git 操作の実装（`src/git/operations.rs`）**: ステージ、コミット、チェックアウトには git2 を用い、フェッチとプッシュのみ Git CLI を呼び出しているが、リモートは origin に固定されている。`create_commit` は `repo.commit` を直接呼び出しているため、Git CLI のフック処理やコミット署名経路を通らない。また、リモートブランチのチェックアウト処理において、同名のローカルブランチが異なる OID を指している場合に強制更新（force update）する処理が存在する。
- **未接続の機能**: マージおよびリベースの `Action` やバックエンド処理は存在するが、通常のキー操作には割り当てられていない。未完成の機能であり、完成済みとして扱ってはならない。

## 初期化の実施範囲（M0）

本ターンでは基盤の初期化に専念し、新 UI の構築や Git 操作の意味論の変更は行わない。
- **識別情報と設定の分離**: 実行ファイル名およびパッケージ名を `lazykeifu`、バージョンを `0.1.0-dev` に設定する。Rust のライブラリ名も `lazykeifu` とする。設定ファイルの配置場所を OS の設定ディレクトリ配下の `lazykeifu/config.toml` に分離し、ログ環境変数を `LAZYKEIFU_LOG` に変更して、元の keifu と安全に併用できるようにする。
- **リポジトリ設定と CI**: `Cargo.toml` に `publish = false` を設定する。upstream から引き継いだ自動リリースワークフローは開発期間中は停止し、無効化ファイル（disabled）として保存する。CI によるフォーマット確認（fmt）、静的解析（clippy）、テスト実行（test）は継続する。
- **ドキュメントの整理**: README をフォーク開発の初期段階である旨と現状の UI が keifu のままである旨を明記した内容に更新する。旧 README は `docs/upstream/README.md` に保持し、元の日本語マニュアルも upstream の参考資料として維持する。
- **基盤検証と反映**: M0 の検証を完了した上で、初期コミットをフォークリポジトリの `main` ブランチへプッシュする予定である。

## 設計方針

- **Git 操作バックエンドの段階的移行**: 読み取り処理およびコミットグラフ生成には既存の git2 を引き続き活用する。変更を伴う書き込み処理は Git CLI を中心とする構成へ段階的に移行する。まずコミット処理（フック実行・署名対応）、チェックアウト処理（意図しない強制更新の排除）、ネットワーク処理から移行を進め、全バックエンドの一括置換は行わない。
- **状態管理と非同期整合性**: アプリケーション全体の構造を事前に過剰分割することはしない。ペインとフォーカス、選択対象（作業ツリーやコミット）、モーダル表示を必要な境界として導入し、UI と Git 実行の間に `Action` を介在させる。非同期処理の結果を受け取る際は対象の OID、ファイルパス、インデックス状態を検証し、遅れて届いた古い結果で現在の選択状態を上書きしない。書き込み処理の実行中は同時並行での状態変更（同時 mutation）を遮断する。

## 段階的実装計画

### M0: リポジトリ初期化と基盤検証
- **実施内容**: パッケージ名・設定パスの分離、リリースワークフローの無効化、フォーク環境の整備。
- **完了条件**: 以下のコマンドによる検証をすべて通過すること。upstream 起因の既存の不具合は適切に切り分ける。
  - `cargo fmt --check`
  - `cargo test --locked`
  - `cargo clippy --all-targets --locked -- -D warnings`
  - `cargo run -- --help`
  - `cargo run -- --version`

### M1: 最初の操作可能版
- **画面構成と操作**: 左ペインにステータス、ファイル一覧、ブランチ一覧を配置する（スタッシュ領域は未実装であることを明示する）。右上にコミットグラフ、右下に差分（diff）を表示する。画面幅が不足する場合はフォーカス対象を優先して描画する。コミットグラフへは `0` や番号キー等で到達可能とする。具体的なペイン番号や配置比率は初回実装時に決定し、ドキュメントおよびヘルプに固定する。基本キー操作として `j` / `k`（上下移動）、`h` / `l` や `Tab`（ペイン移動）、`Space`（ステージング）、`Enter`（詳細表示）、`Esc`（復帰）、`c`（コミット）を提供する。
- **データ表示と安全性改善**: 作業ツリーの変更ファイル一覧とコミット差分一覧を明確に区別し、選択に連動して右ペインの表示を更新する。差分はステージ済みと未ステージを分離して表示する。ファイル表示上限 50 件の制約を解消し、ページ取得または全件一覧表示を可能にする。リモートブランチチェックアウト時の強制更新処理は撤去する（日常利用前の必須条件）。また、基本的な作業ツリー（worktree）環境で正しく起動できることを確認する。
- **完了条件**:
  - ファイル変更の確認、ステージング、差分確認、コミット作成、コミットグラフへの反映という一連の操作が単一ツール内で完結すること。
  - Git フックが失敗した場合はコミットを中止し、入力中のメッセージを保持すること。

### M2: 日常利用版
- **ネットワークとブランチ**: リモートおよび upstream の設定を尊重したフェッチ、プル、プッシュを実装する。プルの実行方針はユーザーの Git 設定を尊重し、暗黙的な強制更新は行わない。ブランチの作成、切り替え、削除をサポートする。
- **変更管理**: スタッシュの保存（save）、適用（apply）、取り出し（pop）、破棄（drop）に対応する。確認ダイアログを伴う変更破棄機能、およびハンク単位のステージングとアンステージングを提供する。
- **マージ・リベースの可視化**: 競合やマージ・リベースの途中状態を表示し、Git CLI や外部エディタへ退避できる導線を設ける。内蔵の対話的競合解決 UI の実装は後段とする。

### M3: 必要性に応じた拡張
日常の利用実績を踏まえ、優先順位を適宜見直しながら以下の実装を検討する。
- cherry-pick、revert、rebase、merge の続行（continue）および中止（abort）。
- 競合解決支援機能。
- 行単位のステージング（line stage）。
- 履歴の追加読み込み処理および大規模リポジトリ向けの最適化。
- git-worktree の高度な操作支援。

## 検証方針と性能評価

- **機能検証**: 各段階において一時的な Git リポジトリ（temporary repo）を作成し、実際の index、tree、refs、および終了ステータス（exit status）を検証する。対象ケースとして、未追跡ファイル、削除、ファイル名変更（rename）、部分ステージング、初回コミット、変更を残した状態のチェックアウト（dirty checkout）、分岐したリモート、フック失敗、51 件以上のファイル変更を含める。
- **UI 検証**: 既存のデバッグサーバを用いた駆動（drive）、ダンプ（dump）、アサート（assert）の仕組みを活用し、画面遷移、狭幅表示、リサイズ処理を検証する。既存のコミットグラフ回帰テストは維持する。
- **性能評価**: 通常規模のリポジトリおよび大規模フィクスチャを用いて、起動時間、キー入力応答、画面更新（refresh）の速度を計測する。「Rust 製だから高速である」といった予断を持たず、まずベースラインの計測を確実に実施し、具体的な数値目標は計測結果に基づいて設定する。

## 未確定事項

以下の項目は現時点で未確定であるが、M0 における初期化作業を阻害するものではない。
- 最終的な正式名称。
- ペインの厳密な番号割り当ておよび画面分割比率。
- lazygit の個人設定ファイルとの互換性（初期実装では lazygit のデフォルト設定を参照し、YAML 設定の完全互換は対象外とする）。
- 最優先で着手すべき高度な機能の選定。
- 動作検証環境（初期は Linux 環境で検証し、CI における他 OS の実行結果は別途確認する）。
